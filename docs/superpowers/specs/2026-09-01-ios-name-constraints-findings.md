# Применяются ли name constraints на iOS — стенд и результаты замеров

Дата: 2026-08-31 — 2026-09-01

## Что выяснялось

Схема obcert держится на том, что клиент применяет `nameConstraints` кросс-подписанного
корня. Для macOS это подтверждалось поведением trustd, для iOS не проверялось никогда.
Настоящий сертификат Минцифры на подконтрольный домен получить нельзя, поэтому нужен был
стенд с подставным корнем, чей приватный ключ у нас.

Итог: **на iOS ограничение применяется, но перенести защиту на iPhone всё равно нельзя** —
цепочка до корня не достраивается. Экспорт профиля из приложения по итогам убран.

## Non-goals

- Настоящий сертификат Минцифры на подконтрольный домен. Невозможно: НУЦ выдаёт по
  заявкам юрлиц, подделать лист без приватного ключа НУЦ нельзя. MITM эмулируется
  подставным корнем со своим ключом.
- Android. `PhoneExporter` уже пишет PEM'ы, но user CA store игнорируется приложениями
  с `targetSdk ≥ 24`, а Firefox Android системный store не читает — отдельная задача.
- Подпись профиля Developer ID. iOS покажет «Не проверено», это остаётся.
- Порт на Windows/Linux.
- Детектор оригинального корня Минцифры на iOS — приложение не имеет доступа к
  системному хранилищу телефона, технически невозможно.

## Текущее состояние

- `AppModel.exportForPhone()` (`App/CheburcertApp/AppModel.swift:101`) реализован:
  берёт `domains` из UI, зовёт `service.buildBundleForExport` (одноразовый ключ,
  который никуда не сохраняется), пишет
  `.mobileconfig` + PEM'ы, открывает Finder.
- `PhoneExporter` покрыт тестами (`Tests/CheburcertCoreTests/PhoneExporterTests.swift`).
- UI-блок вырезан: `App/CheburcertApp/Views/ActionsPane.swift:19-21`.
- Пиннинг отпечатка Минцифры живёт в `CertFetcher`/`MintsifrySource`, **не** в
  `CryptoEngine`. `buildTrustBundle` принимает корень параметром — значит стенд может
  подставить fake-корень, вызывая при этом ровно тот же код сборки бандла.

## Стенд

### Именование

iPhone нельзя дать `/etc/hosts`, поэтому имена берутся из wildcard-DNS, резолвящегося
в LAN-адрес Mac (проверено):

```
ok.192-0-2-10.sslip.io  -> 192.0.2.10
bad.192-0-2-10.sslip.io -> 192.0.2.10
```

IP берётся из `ipconfig getifaddr en0` в момент генерации и записывается в манифест.
Смена сети инвалидирует стенд — сертификаты привязаны к именам.

Альтернатива без третьих лиц: свой домен с wildcard A на LAN-адрес. Дизайн от этого
не зависит, меняется только базовое имя.

### Компоненты

1. **`Sources/obcert-testbed`** — dev-only executable target в `Package.swift`, не
   входит в `.app` (в `App/CheburcertApp/project.yml` не добавляется).
   - генерирует `Fake Russian Trusted Root CA` (RSA-4096 self-signed, как настоящий)
     и `Fake Sub CA`; приватные ключи остаются у стенда;
   - зовёт `CryptoEngine.buildTrustBundle(domains: ["ok.<base>"], mintsifryRoot: fakeRoot,
     mintsifryIntermediates: [fakeSub])` — **код под тестом**;
   - зовёт `PhoneExporter().export(...)` — **код под тестом**;
   - выпускает от `Fake Sub CA` три листа: `ok.<base>` (dNSName SAN),
     `bad.<base>` (dNSName SAN), `<ip>` (iPAddress SAN);
   - пишет всё в каталог из аргумента + `manifest.json` с именами, путями и ожидаемым
     результатом на каждый кейс.
2. **`scripts/testbed-server.py`** — python3 stdlib, `SSLContext.sni_callback` выбирает
   лист по имени, порт 8443 (без sudo), отдаёт страницу с именем хоста, чтобы глазами
   видеть, что открылся именно нужный.
3. **`scripts/testbed-verify.sh`** — машинная проверка на Mac, ничего не устанавливает:
   - Apple trustd (движок Safari и Chrome):
     `security verify-cert -L -N -c leaf -c fakeSub -c crossCert -r localRoot -p ssl -n <host>`
   - OpenSSL: `openssl verify -CAfile localRoot -untrusted <chain> -verify_hostname <host>`
   - NSS: временная БД, наполненная bundled `certutil` из `App/CheburcertApp/Resources`,
     проверка через `vfychain -u 1` (нужен `brew install nss`)
   - итог печатается таблицей PASS/FAIL против `manifest.json`

### Ожидаемая матрица

| Кейс | Ожидание | Что доказывает |
|---|---|---|
| `ok.<base>` | valid | anchor работает, цепочка через кросс-подпись строится |
| `bad.<base>` | invalid, ошибка name constraints | ограничение применяется |
| `<ip>` (iPAddress SAN) | invalid | `excludedIPRanges` применяется |

`ok` и `bad` отличаются **только именем хоста**: один CA, один сервер, один момент
выпуска. Расхождение любого верификатора с этой таблицей — находка, а не баг стенда.

### Ручной прогон на iPhone

1. AirDrop `obcert-test.mobileconfig` на iPhone.
2. Настройки → Профиль загружен → Установить. «Не проверено» ожидаемо.
3. Настройки → Основные → Об этом устройстве → Доверие сертификатам → включить корень.
4. Safari: три URL из матрицы, порт 8443.
5. Ctrl-C на сервере — он напечатает вердикт и запишет его в `--report`.
6. Удалить тестовый профиль.

Safari на iOS не показывает код ошибки, поэтому вердикт выносится не по виду экрана, а по
тому, что зафиксировал сервер: `served` (клиент доверился), `handshake rejected by client`
(клиент отверг сертификат — доказательство), отсутствие подключения (`NOT TESTED`).
Запросы с самого Mac в вердикт не попадают.

### Результаты прогона на устройстве

Прогоны r1–r6, iPhone (iOS 26), стенд `obcert-testbed` + `scripts/testbed-server.py`.
Сырые события сохранены в `phone-report.json` каждого прогона.

**Установлено два факта.**

**1. iOS применяет `nameConstraints`.** Решающая пара — r6:

| Кейс | Цепочка от сервера | Имя | Телефон |
| --- | --- | --- | --- |
| `okfull` | лист + sub CA + кросс | разрешено | открылся |
| `badfull` | лист + sub CA + кросс | запрещено | отвергнут |

Состав цепочки, якорь и момент выпуска совпадают; отличается только имя. Значит
отвергло именно ограничение.

**2. iOS не использует установленный профилем промежуточный сертификат для построения
пути — вообще, а не только наш кросс-сертификат.**

Сначала пара `ok` / `okfull` (прогон r6, кросс-подпись и ограничения на месте):

| Кейс | Кросс-сертификат | Телефон |
| --- | --- | --- |
| `okfull` | в цепочке от сервера | открылся |
| `ok` | только в профиле (`com.apple.security.pkcs1`) | отвергнут |

Оставался вопрос, не виноват ли сам кросс-сертификат: он делит subject и SKI с корнем,
которого в хранилище нет, и несёт критический `nameConstraints` на CA. Раскладка
`plainIntermediate` убирает все три особенности — обычный самоподписанный корень, обычный
промежуточный, лист, никаких ограничений:

| Кейс | Промежуточный | Телефон |
| --- | --- | --- |
| `plainfull` | в цепочке от сервера | открылся |
| `plain` | только в профиле | **отвергнут** |

Результат тот же, значит свойство общее: **сертификат, установленный профилем без доверия,
iOS для достройки цепочки не использует.** Это выходит за рамки obcert — любой частный PKI,
доставляемый конфигурационным профилем, обязан присылать полную цепочку с сервера.

**Следствие для продукта.** Настоящий сайт Минцифры присылает `лист + sub CA`;
кросс-сертификат обязан подтягиваться из хранилища. Значит выгруженный профиль на iPhone
**не даёт доступа к сайтам** — корень доверен, ограничение работает, а путь не строится.
Это не дыра в безопасности, но и не работающая функция.

**Для сравнения: на macOS поиск в хранилище работает.** `security verify-cert` с одним
листом достраивает путь, если промежуточные лежат в keychain из search list, и не
достраивает, если они в хранилище вне списка. То есть механизм на платформе есть, и
различие именно в профильных сертификатах iOS.

**Способы доставки кросс-сертификата — оба проверены и оба закрыты.**

| Вариант | Замер | Итог |
| --- | --- | --- |
| `com.apple.security.pem` вместо `pkcs1` | `okfull` открылся (якорь доверен), `ok` отвергнут в той же сессии | кодировка ни при чём, поиск в хранилище всё равно не происходит |
| кросс-сертификат как `com.apple.security.root` | профиль установлен, сертификат в нём отображается (iOS показывает издателя — значит видит, что он не самоподписан), но в «Доверие сертификатам» записи нет | **закрыто**: доверие включить негде |

Схема требует, чтобы ровно один несамоподписанный сертификат пришёл из хранилища, и на
проверенных путях доставки iOS его оттуда не берёт. Любая перестановка (кросс-подпись
sub CA вместо корня, совпадающий subject у локального корня) сводится к тому же
требованию — но «нереализуема в принципе» пока не доказано: доказано только то, что
`pkcs1` и `pem` не работают, а вариант с якорем не измерен.

Если гипотеза про самоподписанность подтвердится, вариант с якорем закрыт и в проде:
якорь обязан нести публичный ключ НУЦ (иначе не проверит подпись sub CA), а самоподписать
такой сертификат можно только приватным ключом НУЦ.

**Итог: путей не осталось.** Якорь обязан либо проверять подпись sub CA (то есть содержать
публичный ключ корня НУЦ), либо быть самим sub CA. Оба несамоподписаны, а несамоподписанному
iOS доверять не даёт. Самоподписать сертификат с публичным ключом НУЦ можно только их
приватным ключом.

**Что осталось выяснить.** Меняет ли дело провенанс MDM. Найденный блокер — ограничение
интерфейса: нет переключателя, нечего включить. Корень из MDM-профиля доверяется **без**
переключателя, то есть MDM обходит ровно это место. Но device-wide корни ставит только
Device Enrollment, а он даёт и удалённое стирание; ограниченный User Enrollment сертификатные
payload'ы не поддерживает. Для корпоративных развёртываний применимо, для приложения
обычного пользователя нет.

**Единственный путь, укладывающийся во все найденные ограничения** — локальный прокси:
он завершает цепочку сам и отдаёт телефону сертификат от **самоподписанного** корня, для
которого переключатель появляется, а `nameConstraints` на нём iOS применяет (измерено).
Это другой продукт, не кнопка в приложении. Корень из MDM-профиля доверяется
без ручного переключателя, то есть iOS уже различает профили по происхождению; не исключено,
что различие распространяется и на использование сертификатов при построении пути. Замер:
тот же стенд, тот же разграничитель (`ok` против `okfull`), профиль доставлен MDM-сервером.
Подделать провенанс редактированием файла нельзя — он не выражается ключом в plist.

Оговорка: даже подтверждённая, эта гипотеза вряд ли даёт продуктовую функцию. obcert —
приложение для обычного пользователя и не может записывать телефон в MDM: это отдаёт
устройству управление целиком, что хуже решаемой задачи. Ценность была бы в корпоративных
развёртываниях и в понимании механизма.

Также не измерено: держится ли `excludedIPRanges` на iOS — IP-кейс во всех прогонах шёл без
кросс-сертификата и падал на построении пути.

**Ошибки процедуры, найденные по пути** (каждая давала неверный вывод до исправления):
продавленное предупреждение засчитывалось как доверие; Safari помнит исключения по имени
хоста, поэтому повторный прогон воспроизводил прошлое решение; тестовый и рабочий профиль
имели одинаковый `PayloadIdentifier` и CN корня, из-за чего первый молча заменял второй и
их нельзя было различить в настройках; контрольным кейсом брался несопоставимый.
