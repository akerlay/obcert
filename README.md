**Доверяй корневому сертификату Минцифры РФ только для нужных доменов.**

obcert — приложение для macOS. Оно позволяет открывать российские сайты, которые
отдают TLS-сертификаты Минцифры (Госуслуги, банки и т.п.), **не** давая при этом
государственному корневому сертификату возможность подписывать сертификаты для
всего остального интернета. Вы указываете список доменов — и сертификаты Минцифры
принимаются только для них и их поддоменов.

- Скачать .dmg из [releases](https://github.com/akerlay/obcert/releases/latest)
- Запустить .dmg и перетащить obcert в Applications

## Как это работает

При полном доверии к корню Минцифры государство технически может выпустить
валидный сертификат для **любого** домена — то есть незаметно перехватывать (MITM)
любой HTTPS-трафик. obcert заменяет безусловное доверие на доверие с ограничением.

1. **Локальный ограниченный корень.** Приложение генерирует на вашем компьютере
 новый корневой центр сертификации (приватный ключ никуда не уходит) с
 критическим расширением `nameConstraints`, где в списке разрешённых —
 только ваши домены (и `excluded` для всех IP-адресов).
2. **Кросс-подпись корня Минцифры.** Приложение берёт настоящий корень Минцифры и
 выпускает его «двойника»: с тем же субъектом, тем же публичным ключом, тем же
 Subject Key Identifier и серийным номером — но подписанного **вашим** локальным
 корнем (эквивалент `openssl x509 -force_pubkey`). Настоящий безусловный корень
 Минцифры в хранилище доверия **не добавляется**.
3. **Цепочка достраивается через ограничение.** Реальный сертификат российского
 сайта строит путь `сайт → промежуточный Минцифры → двойник → ваш локальный  корень`. Ваш корень доверенный, но его `nameConstraints` разрешают только
 перечисленные домены. Сертификат Минцифры для домена вне списка не проходит
 проверку.

Приложение устанавливает это в системное хранилище macOS (Keychain — Safari,
Chrome) и в хранилище NSS каждого профиля Firefox (через встроенный `certutil`).

### Важное условие: оригинал Минцифры не должен быть доверенным

Ограничение работает во всех браузерах **при условии**, что в системе не установлен
доверенным **оригинальный, неограниченный** корень Минцифры — иначе сертификат
Минцифры для любого домена пройдёт проверку напрямую по нему, в обход ограничения.

Поэтому при запуске obcert проверяет наличие оригинального корня Минцифры (по
закреплённому отпечатку SHA-256, что отличает его от нашего «двойника» с тем же
именем) и, если находит, **блокирует работу** до его удаления — с кнопкой удаления
в один клик (запросит пароль администратора).

## Возможности

- Список разрешённых доменов; каждый домен автоматически включает все поддомены
(`sberbank.ru` покрывает `online.sberbank.ru` и т.д.). Поддерживаются зоны
(`.ru`) и кириллица (`.рф` → Punycode).
- Готовые наборы: «Госуслуги», «Крупные банки», «Весь .ru / .рф / .su».
- Установка во все браузеры одним нажатием (macOS попросит подтвердить доверие  
сертификату — пароль пользователя, без прав администратора).
- Кнопка полного удаления всего установленного.
- Блокировка при обнаружении оригинального корня Минцифры + его удаление.

## Телефон (iPhone) — не поддерживается

Экспорт профиля для iPhone **убран из приложения**. Замер на iOS 26 показал, почему он не
может работать:

| Что измерено | Результат |
| --- | --- |
| iOS доверяет ограниченному корню из профиля | да |
| iOS применяет `nameConstraints` (разрешённое/запрещённое DNS-имя) | **да** |
| iOS использует установленный профилем промежуточный сертификат для построения пути | **нет** — ни кросс-сертификат, ни обычный |

Настоящий сайт Минцифры присылает только `лист + sub CA`. Кросс-сертификат, связывающий
их с вашим корнем, обязан подтягиваться из хранилища — и не подтягивается, поэтому цепочка
не достраивается и сайты не открываются.

Свойство общее, а не особенность кросс-сертификата: обычный трёхуровневый PKI без
кросс-подписи и без ограничений имён ведёт себя так же — лист с промежуточным от сервера
открывается, лист без него отвергается. Для сравнения, на macOS промежуточный из keychain
находится и путь достраивается.

Все способы доставки проверены и закрыты:

| Способ | Результат |
| --- | --- |
| кросс-сертификат как `com.apple.security.pkcs1` | не используется при построении пути |
| он же как `com.apple.security.pem` | то же самое, кодировка ни при чём |
| кросс-сертификат как `com.apple.security.root` (якорь) | профиль ставится, сертификат в нём виден, но в «Доверие сертификатам» он не появляется — iOS предлагает доверять только самоподписанным корням |

Последняя строка замыкает вопрос. Чтобы достроить цепочку, нужен сертификат, проверяющий
подпись sub CA, то есть содержащий публичный ключ корня НУЦ, — либо сам sub CA. Оба
несамоподписаны по построению, а самоподписать сертификат с публичным ключом НУЦ можно
только их приватным ключом.

Кнопка убрана намеренно, а не «до лучших времён». Неработающий профиль ломает доступ к
сайтам и тем самым подталкивает поставить **неограниченный** корень Минцифры — то есть его
отказ хуже, чем отсутствие функции. Код генерации профиля (`PhoneExporter`) остался: он
корректен, покрыт тестами и используется стендом.

Сырые данные шести прогонов и список найденных по пути ошибок —
в [дизайн-документе](docs/superpowers/specs/2026-09-01-ios-name-constraints-findings.md).

### Стенд проверки ограничения

Проверяет, что ограничение реально применяется — включая проверку с iPhone. Настоящий
сертификат Минцифры на подконтрольный домен получить нельзя, поэтому MITM эмулируется
подставным корнем, приватный ключ которого у нас:

```bash
BED=$(mktemp -d)
swift run obcert-testbed --out "$BED"          # подставной PKI + профиль + три листа
bash scripts/testbed-verify.sh "$BED"          # trustd / OpenSSL / NSS (brew install nss)
python3 scripts/testbed-server.py --manifest "$BED/manifest.json" \
        --report "$BED/phone-report.json" &    # для проверки с телефона
```

Сервер держите в фоне (`&`): прогон занимает столько, сколько нужно на установку профиля
и три URL руками, а отчёт обновляется после каждого события и читается не останавливая
сервер — так его не потерять, если процесс убьёт таймаут или закрытый терминал.

Имена (`ok.<ip>.sslip.io`, `bad.<ip>.sslip.io`) резолвятся в LAN-адрес Mac, поэтому те же
три URL открываются и с телефона — `/etc/hosts` не нужен. Установите
`$BED/obcert-test.mobileconfig`, включите полное доверие, откройте URL из вывода, потом
Ctrl-C.

Сервер печатает вердикт по тому, что телефон **сделал**, а не по тому, что вы увидели.
Это важно: Safari на iOS не показывает код ошибки, поэтому «страница не открылась»
означает одно из двух, и со стороны телефона они неразличимы:

| Что видно с сервера | Вывод |
| --- | --- |
| хендшейк прошёл, запрос отдан | клиент доверяет цепочке |
| подключение было, хендшейк отвергнут | клиент отверг сертификат — **это и есть доказательство** |
| подключения не было | не проверено ничего: DNS или сеть |

Третий случай помечается `NOT TESTED`, а не `PASS`. Запросы с самого Mac в вердикт не
попадают, чтобы локальную пробу нельзя было принять за проверку с телефона. Логика
вердикта покрыта тестами: `python3 scripts/testbed-server-test.py`.

Каталог `$BED` содержит приватный ключ подставного CA — удалите его и тестовый профиль с
телефона после прогона. Тестовый и рабочий профиль нельзя держать вместе: у обоих корень
с одинаковым CN, в настройках iOS их не различить.

7. Нажмите **Удалить всё** — статус вернётся в «Защита выключена»; в Firefox
 (Настройки → Приватность и защита → Сертификаты → Просмотр → Центры
 сертификации) корень «obcert Local Constrained Root» исчезнет.

## Архитектура (для разработчиков)

- `**CheburcertCore**` — библиотека Swift Package (вся логика, покрыта тестами):
нормализация доменов, крипто-движок (`nameConstraints` + кросс-подпись),
скачивание и пиннинг сертификатов, установщики Keychain и Firefox, детектор
оригинального корня, экспорт для телефона, оркестрация.
- `**App/CheburcertApp**` — тонкий SwiftUI-слой (одно окно) поверх библиотеки,
плюс вложенный `certutil` для Firefox.
